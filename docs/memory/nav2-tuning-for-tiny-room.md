**2026-08-07 확정.** 온보드 Nav2 로 옮긴 직후 "목표를 줘도 못 간다 / 중앙을 찍었는데 오른쪽 벽으로 간다"가 나왔다. 원인은 보드도 라이다도 환경도 아니라 **Nav2 기본값이 이 방 크기에 안 맞는 것**이었다. 두 값을 고치자 `Reached the goal!` 이 두 번 연속 나오고 오류가 0 이 됐다.

## 고친 값 (`config/patrol_nav2.yaml`)

| 값 | 전(기본값) | 후 | 왜 |
|---|---|---|---|
| `progress_checker.required_movement_radius` | 0.5 | **0.10** | "10초에 0.5m 이상 이동" 조건. 순찰 사각형이 1.15x0.95m 이고 `max_vel_x` 를 0.10 으로 낮췄으니 10초 최대가 1.0m, 코너 정지까지 하면 훨씬 짧다. **목표 간 거리가 20cm 대면 수학적으로 불가능** |
| `progress_checker.movement_time_allowance` | 10.0 | **20.0** | 위와 같은 이유 |
| `amcl.update_min_d` | 0.25 | **0.05** | "25cm 이동마다 한 번 보정". 웨이포인트 사이가 95cm 면 보정 3~4번, 20cm 목표면 **0번**이다. 보정을 못 하면 틀린 위치를 믿고 달린다 |
| `amcl.update_min_a` | 0.2 | **0.05** | 같은 이유(11.5도 → 2.9도마다) |

**아직 안 건드린 예비안(C):** `max_beams` 60→180, `alpha1~5` 0.2→0.05, `laser_max_range` 100.0→3.5. 위 두 개만으로 해결됐으므로 남겨뒀다. 나중에 매칭이 불안하면 여기서부터.

## 2차 조정 — 속도를 올린 것이 progress 문제의 실질적 해법이었다

사용자가 "안전모 때문에 늦춘 속도를 다시 올려보자"고 제안해 `max_vel_x` **0.10 → 0.15** (+`max_speed_xy` 동일), `movement_time_allowance` **20 → 40** 을 적용했다. 순찰 1바퀴 실측 비교:

| 구간 | 1차 (0.10 / 20s) | 2차 (0.15 / 40s) |
|---|---|---|
| 시작지점 → 우상 | 96초 | **45초** |
| 우상 → 우하 | 23초 | **10초** |
| 우하 → 좌하 | 24초 | **15초** |
| 좌하 → 좌상 | 23초 | **15초** |
| **총** | **3.1분** | **1.9분** |
| **`Failed to make progress`** | **4회** | **1회** |
| 복구 동작 | 5회 | 1회 |

**⚠️ `max_vel_x` 0.15 는 잠정값이다.** "안전모 판정이 빨라져서"가 아니다 — Pi 4 온보드 추론은 실측 **405ms/장(2.5fps)** 이라 VM 보다 오히려 느릴 수 있다. 올린 근거는 progress_checker 뿐이므로, **안전모 판정을 온보드로 켠 뒤 판정이 따라오는지 재서 최종값을 확정**해야 한다. 0.10 은 2026-08-02 실측으로 정한 값이다.

## 남은 문제 — 첫 구간(좌상 → 우상)만 3배 느리다

2차에서도 `좌상 → 우상` 45초 vs `우하 → 좌하` 15초. **둘 다 1.15m 같은 거리**이므로 거리 문제가 아니다. 남은 `Failed to make progress` 1회도 시각 대조 결과 **이 구간 안**이었다(22:40:25, 구간 22:39:48~22:40:33).

`patrol_node.py:340` 을 확인한 결과 **yaw 문제는 아니다** — 시작지점 목표는 `next_idx` 없이 보내져 웨이포인트에 저장된 yaw(좌상은 0.0 = +x)를 쓰고, 우상은 좌상에서 정확히 +x 방향이라 큰 회전이 필요 없다.

### 지도에서 계산한 웨이포인트별 실제 여유 (2026-08-07, `patrol_map_v5`)

| 지점 | 좌표 | 가장 가까운 장애물까지 |
|---|---|---|
| **좌상** | (+0.160, −0.270) | **0.270m** ← 유일하게 좁다 |
| 우상 | (+1.310, −0.270) | 0.350m |
| 우하 | (+1.310, −1.220) | 0.350m |
| 좌하 | (+0.160, −1.220) | 0.350m |

**좌상이 좁은 것은 의도된 것이다 — 그 장애물이 소화기이고, 압력계를 읽으려고 일부러 가깝게 잡았다.** 따라서 **웨이포인트를 옮기는 것은 해법이 아니다**(점검 대상에서 멀어진다). 어시스턴트가 "v5 지도로 웨이포인트를 재계산하자"고 제안했다가 이 이유로 철회했다.

### 제거된 가설들 (좌상 구간 문제의 원인이 아님)

- **`robot_radius` 가 Nav2 기본값(0.22)일 것** → 실제로는 `0.1` 로 이미 올바르게 설정돼 있다(local·global 양쪽 런타임 확인). Burger 실제 반경 0.105 와 맞다
- **`inflation_radius` 안에 웨이포인트가 잠긴 것** → 0.270m 는 `inflation_radius` 0.25 **바로 밖**이라 웨이포인트 칸 자체의 비용은 0 이다
- **웨이포인트가 지도보다 낡은 것** → 시간 순서(웨이포인트 14:28, 지도 v5 17:47)로 그렇게 추정했으나, 좌상이 좁은 건 소화기 때문이므로 무관하다

**남은 유력 가설:** 소화기와 **local costmap** 의 상호작용. 복구 동작이 `clear entirely the local_costmap` 하나뿐이었고 그것이 매번 진행을 풀어줬다 — 국소 코스트맵에 누적된 표시가 출발을 막고, 비우면 잠깐 풀리는 패턴이다. 확인에는 주행 중 코스트맵을 들여다봐야 한다.

## ⚠️ 지도 자체의 문제 — 벽 밖이 "주행 가능"으로 기록돼 있다

`patrol_map_v5.pgm` 을 분석한 결과: **133x124 화소(41.2m²) 중 점유는 878개뿐이고 나머지 15614개(39.04m²)가 전부 흰색(자유)** 이다. 벽선에 틈이 있어 **방 안과 벽 밖이 하나의 연결 성분**으로 이어져 있다(기준점에서 flood fill 하면 39m² 전체가 잡힌다 — 메모의 "빈공간 6.56m²"와 전혀 다르다).

**의미:** Nav2 는 **벽 밖도 갈 수 있는 공간으로 알고 있다.** 방 밖에 목표를 찍으면 받아들이고 벽을 향해 밀어붙인다. "중앙을 찍었는데 벽으로 갔다"의 일부가 이것과 관련될 수 있다.

**부수 효과:** 이 때문에 "30cm 여유 최대 사각형"을 지도에서 다시 계산하려는 시도가 전부 방 밖을 가리켜 실패했다. 웨이포인트를 계산으로 다시 뽑으려면 **먼저 지도에서 벽 밖을 미탐사(회색 205) 또는 점유로 칠해야** 한다.

## 왜 예전에는 안 드러났나 — 중요한 오진 이력

`Failed to make progress` 를 **무선 지연 증상으로 분류해뒀었다**([[wireless-is-the-bottleneck]]). Nav2 가 VM 에 있던 동안은 무선으로 인한 스캔 유실과 이 값 문제가 **같은 증상**을 냈기 때문이다. **Nav2 를 로봇 온보드로 옮겨 무선을 변수에서 제거하니 진짜 원인이 드러났다.** 증상이 겹치는 원인이 둘 있을 때, 하나를 제거해야 다른 하나가 보인다.

또한 `max_vel_x` 를 0.22 → 0.15 → 0.10 으로 낮춘 것(안전모 판정용, [[helmet-detection-color-tape-solution]])이 progress_checker 를 점점 만족 불가능하게 만들었다. **속도를 낮출 때는 progress_checker 도 같이 봐야 한다** — 이 둘은 묶여 있다.

## 대가 (실측)

`update_min_d` 를 5배 촘촘하게 하면 AMCL 이 5배 자주 돈다: **Nav2 CPU 44.8% → 81.3%** (Pi 4 4코어의 약 20%). 온도 45→59°C, `throttled=0x0` 유지. **이 여유는 Pi 4 라서 낼 수 있다** — VM 2코어에서 이 설정을 썼다면 안전모 추론과 정면충돌했을 것이다.

## 이 방에서 헛다리 짚은 것들 (다시 의심하지 말 것)

2026-08-07 에 하나씩 측정으로 제거했다:

1. **라이다 장착 각도** — 소화기를 정면 25cm 에 두고 스캔을 읽으니 **350~5도에 고립된 호**로 잡혔다(양옆은 1.4~1.7m). 정상 장착이다. *판정법: 물체를 정면 15~25cm 에 두고 최단거리 각도를 본다. 로봇을 움직이며 재는 방법은 노이즈가 커서 결론이 안 난다*
2. **odom 고장** — 15cm 전진 명령에 odom 이 0.153m 를 기록. 정확하다. *단 토크를 끄면 odom 이 이동을 못 잡는다 — 손으로 밀어 시험할 때 이걸 모르면 오진한다*
3. **자이로 바이어스** — 정지 상태 10초에서 `angular_velocity.z` 평균 0.00000 rad/s, odom yaw 변화 0.001도. 깨끗하다(`diff_drive_controller` 는 `odometry.use_imu: true` 로 자이로를 쓴다)
4. **바퀴/URDF 파라미터** — `wheels.separation 0.16`, `wheels.radius 0.033`, `base_link->base_scan` 회전 0. 전부 표준값
5. **카펫·정사각형 방 대칭** — 그럴듯했지만 **Pi 3 때 같은 조건에서 잘 됐으므로 원인이 될 수 없다.** 사용자가 이 점을 지적해 코드/설정 쪽으로 방향을 돌린 것이 해결의 계기였다

## 2026-08-14 실주행 재현 — "첫 구간 정체"의 유력 원인 특정 (소화기 가설 후순위로)

온보드 Nav2 첫 실주행에서 첫 구간(좌상→우상) `Failed to make progress` **4연속**(정확히 40초 한도마다 = 사실상 완전 정지 160초), 90° 회전 복구 직후 22초 만에 도달, 이후 전 구간 11~13초로 정상.

**증거와 재구성:**
- "No valid trajectories" 0건 — 막힌 게 아니라 DWB가 0속도 궤적만 계속 채택 (오류 로그 없는 정지)
- 사용자 목격: 로봇 완전 정지 → 회전 후 갑자기 정상 주행. 사람은 근처에 없었음
- 복구 직후 AMCL 위치 (0.59, −1.10) = START에서 80cm 이상 남쪽 — 이후 구간 소요시간과 전부 정합 → 이게 **참값**이고, 초기 위치 힌트(START)가 실제 놓인 위치와 어긋나 있었던 것
- 정적 지도 통로 분석: 구간 1 평균 여유 0.39m로 구간 3(0.32m, 13초 통과)보다 넓음 → 구조적 병목 아님

**메커니즘:** 초기 위치 힌트가 실제와 어긋남 → 믿는 경로와 실제 스캔 장애물이 불일치 → DWB 전진 궤적 저평가 → 0속도 교착 → 이동이 없으니 AMCL 보정도 안 됨. **회전만이 이동 없이 AMCL 갱신(update_min_a 2.9°)을 강제해 교착을 푼다.** costmap 비우기 복구는 3회 무효과였음(8-07의 "비우기가 풀어줬다"는 관찰은 우연일 가능성). 첫 구간만 느린 이유 = 첫 구간이 항상 "초기 위치를 방금 찍은 직후"라서.

**해법(다음 주행에서 검증):** 초기 위치 지정 → **순찰 시작 전 제자리 ±90° 정렬 회전**(/spin 액션) → AMCL 수렴 확인 → 순찰 시작. 합격 기준: 첫 구간 45초 이내 + FTMP 0회. 검증되면 patrol_node 에 파라미터로 코드화 검토. 보조 계측으로 AMCL 위치 초 단위 로거를 붙여 위치 도약을 직접 확인할 것.
