## 왜 바꾸는가 — 진짜 원인은 CPU 가 아니라 구조였다

지금 구조는 로봇(Pi 3)이 영상·센서만 무선으로 보내고, **자율주행 계산(Nav2)과 안전모 인식(딥러닝)을 전부 VM 이 대신 처리**한다. Pi 3 가 약해서 어쩔 수 없이 택한 우회였다. 그런데 이 구조 자체가 실측으로 확인된 문제들의 원인이었다:
- VM→공유기 무선 200ms (로봇→공유기는 29ms로 멀쩡) → `/scan` 이 TF 캐시를 벗어나 버려짐 → Nav2 목표 거절 ([[wireless-is-the-bottleneck]])
- VM 이 2코어뿐이라 Nav2 와 안전모 추론이 CPU 를 다퉈 순찰 한 구간이 16초→107초로 늘어난 적 있음 ([[helmet-detection-color-tape-solution]] 참고)

**HI-CEED 강사(임기태 강사님)의 피드백이 결정적이었다:** "VM은 그냥 영상을 보여주는 역할이고, 실제 계산이랑 영상 처리는 라즈베리파이에서 하는 것" — 즉 Nav2 만 로봇으로 옮기는 게 아니라 **안전모 인식(딥러닝 추론)까지 전부 로봇으로 옮기고, VM은 순수 디스플레이/대시보드로만 남기는 게 목표 구조**다. 이게 이전에 내(어시스턴트)가 제안했던 "Nav2 만 온보드, 인식은 VM 유지" 하이브리드안을 대체한다.

강사님의 두 번째 코멘트: "thread 처리를 잘해야 함. 결국 round robin을 어떻게 구현하느냐의 싸움임." — 보드를 바꿔도 소프트웨어가 여러 작업(모터 제어·라이다·카메라·Nav2·추론)에 CPU 시간을 잘 나눠주지 못하면 여전히 멈춘다는 경고다. **Pi 4 이식 작업의 핵심은 ROS2 MultiThreadedExecutor + callback group 설계**이지, 단순히 코드를 로봇에 복사하는 게 아니다. VM 에서 이미 겪은 CPU 경쟁 문제(위 16초→107초)가 Pi 4 안에서 재발할 수 있다는 뜻 — 그때 쓴 완화책(`nice +10`, `cv2.setNumThreads(1)`)이 사실 수동 스케줄링 개입이었다.

## 실제 구매 완료 (2026-08-07)

| 품목 | 비고 |
|---|---|
| 라즈베리파이 4 Model B **2GB** | **실구매는 2GB.** 검토 중엔 "VM=화면만" 목표에 맞춰 4GB(183,700원)를 권했으나, 최종 구매는 2GB로 확정됨(96,800원) |
| microSD **64GB A1등급** | 구매 완료 |
| 방열판 (구리) | 구매 권장했음 — 실제 구매 여부는 다음 세션에서 확인할 것 |

**2GB로 산 것에 대한 판단** — 걸림돌은 아니다. 실측(VM 기준) 안전모 추론 175MB, Nav2 126MB 라 2GB에도 다 들어가고 여유가 남는다(계산상 700MB~1.1GB 사용, 2GB의 절반 수준). "VM=화면만, 계산 전부 로봇" 목표를 2GB로도 그대로 진행할 수 있다 — 다만 앞으로 기능(안전조끼·QR·야간·금지구역)이 쌓이면서 여유가 4GB보다는 빠듯해질 수 있으니, 메모리 부족 징후(스왑 발생, 급격한 속도 저하)가 보이면 그때 4GB 교체를 다시 고려한다. 구매요청서(`pi4_purchase_request.docx`)에는 4GB 기준으로 써서 전달했으나, 실제로는 2GB를 산 것이므로 담당자에게 실제 구매액을 다시 확인시켜줄 필요가 있을 수 있음.

**함께 안 사기로 한 것:** 케이스(TB3 판에 직결 마운트라 불필요), 카메라모듈(Pi 3/4 는 같은 15핀 CSI 커넥터라 기존 imx219 리본 그대로 호환), 아답터(기존 5V 3A USB-C 충전기로 충분), 케이블.

## SD카드 — 복제 대신 새로 굽고 데이터만 옮긴다

지금 로봇 카드(SanDisk Ultra 16GB, 모델 SC16G, 2018-10 제조, **실물 확인 결과 A1 표시 없음**, 80%참/2.8GB 여유)는 그대로 로봇에 남겨 백업으로 쓴다. **새 64GB A1 카드는 구매 완료(2026-08-07).** 새 카드는:
1. 사용자가 **Raspberry Pi Imager**로 새 64GB A1 카드에 Ubuntu 22.04 를 깨끗하게 새로 굽는다 (dd 복제 아님 — 기존 카드의 로그·잡동사니를 안 옮기려는 의도)
2. 로봇 부팅 후 IP 를 MAC(`b8:27:eb:9f:73:ec`)으로 찾아 ssh 접속
3. 어시스턴트가 원격으로 ROS2 Humble + turtlebot3 + Nav2 패키지 설치
4. `~/vibe/ex1/`(VM)에 있는 지도·웨이포인트·안전모 색 기준·압력계 기준·코드·모델 파일을 로봇으로 복사
5. 실제 새 작업(Nav2/추론을 로봇에서 돌리는 launch 구성, threading 설계)은 여기서부터 시작 — 이건 데이터 복사로 되는 게 아니라 새로 만들어야 하는 부분

## 챙길 것 — 다음 세션 시작 시

- 구매 승인/규정 확인 결과가 어떻게 나왔는지 (대회 규정 위반 여부, 지원금 증액 여부) 사용자에게 먼저 물어볼 것
- **라즈베리파이4(2GB)와 64GB A1 SD카드는 구매 완료(2026-08-07).** 방열판 구매 여부와 Raspberry Pi Imager 로 새 카드에 Ubuntu 22.04 굽기 완료 여부는 다음 세션에서 확인할 것
- 로봇 IP는 매번 바뀌므로 [[robot-host-identity]] 방식으로 재탐색
- VM 쪽 미적용 완화책 두 가지가 아직 남아있음(이번 세션에서 권했지만 실행 여부 미확인): VM 코어 2→4, `transform_tolerance` 완화. Pi 4 온보드로 가면 이 VM 튜닝의 필요성 자체가 줄어들 수 있으니, Pi 4 작업 전에 먼저 확인할 것
- 라인 추종 재검토는 최종적으로 기각됨 — 장소가 바뀔 수 있다는 우려에는 "그 자리에서 cartographer 로 재매핑"(30분~2시간)이 답. 이유: 카메라 각도 재조정 문제, 장애물 회피가 라인 추종에서 더 어려움, 결정적으로 **로봇 좌표(AMCL)가 없어져 야간 순찰의 금지구역 기능이 아예 불가능해짐**. 다시 제안하지 말 것 ([[nav2-not-line-following]] 참고, 이번에도 같은 결론 재확인됨)

## 남은 확장 기능 (Pi 4 작업 이후)

우선순위·의존관계:
1. 안전조끼 인식 — 안전모와 같은 색 판정 구조, 몸통 영역. 가장 쉬움
2. 소화기 QR 점검 — 도구는 반쯤 있음(`make_qr.py`, zbarimg 검증 완료). 라벨 내용연한 확정 → 인쇄 → 부착 → 판독거리 확인 남음
3. 웹 대시보드 — 지금 CSV·사진 로그를 모아 보여줌. VM 에서 돌리는 게 맞음(로봇 자원 안 씀). 지금 바로 시작 가능
4. 야간 순찰 — **조명이 관건.** IR/NoIR 카메라는 낮 색 판정(초록 테이프 HSV)이 깨질 위험이 커서 권장 안 함. 가시광 LED 추가가 안전. 다만 "몰래 포착"이 목적이면 가시광이 오히려 방해(침입자가 봄) — 목적(억제 vs 포착)을 먼저 정할 것
5. 금지구역 침입 감지 — 로봇 좌표 기준(쉬움, AMCL 필요)으로 하기로 함. 사람 위치 기준(카메라로 거리 추정)은 어려워서 보류
